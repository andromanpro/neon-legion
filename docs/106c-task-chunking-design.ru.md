# #106-C — убрать «1 сессия = 1 задача»: проектное предложение (ревью до кода)

Статус: **ДИЗАЙН — код не написан.** Гейт для твоего решения перед любой реализацией.
(Канонический английский: [`106c-task-chunking-design.md`](106c-task-chunking-design.md) — для Codex/других агентов по конвенции репо. Эта версия — для ревью.)

## Почему это последний реальный рычаг

`#106` разложился на: #106-A (high-end stub guard — отгружен, детерминированный), #107 (денумератор — отгружен), #106-B (size-aware оракул — отгружен, честно описан как «скромный»), #106-D (перепрогон истории — закрыт как moot), **#106-C (это).**

Исходный 3-way анализ относил **~80% искажения числителя на модель данных**, а не на оценщик: `tracker/tasks.json` ключуется по `session_id`, поэтому сессия Claude Code, растянутая на дни и содержащая десятки разных задач, получает ровно **один** `ai_baseline_hours`. #106-B эмпирически подтвердил, что формулировкой промпта это не лечится — сессия на 5118 событий и 5 дней, сжатая в одно число оракула, и лоссильна, и шумна (±22ч от прогона к прогону) при любом качестве промпта. Единственный структурный фикс — перестать считать сессию единицей работы.

## Три варианта (меню из issue, с трейд-оффами)

### C1 — Чанкинг по календарным дням (рекомендуемый первый шаг)
Резать события сессии по календарным дням; единица оценки = `(session_id, YYYY-MM-DD)`. Один марафон → N дневных чанков → N baseline'ов, суммируются.

- **Бэкфиллится**: выводится чисто из таймстампов событий, уже лежащих в JSONL. Новый сбор данных не нужен; историю можно перечанковать.
- **Без правок hook / UX**: хуки SessionStart/Stop не трогаются; дисциплина пользователя не требуется.
- **Blast radius: умеренный** (см. ниже).
- **Ограничение**: день — это прокси «задачи», не настоящая граница задачи. День с 3 несвязанными задачами всё ещё получит одну оценку (но *гораздо* лучше отскоупленную, чем на 5-дневную сессию).

### C2 — Явные границы задач (task-id / тег Gitea-issue)
Хук или пользователь помечает границы задач; одна сессия → явные task-записи.

- **Максимальная точность** — настоящие единицы-задачи.
- **Не бэкфиллится** — исторических тегов задач нет; улучшает только *будущие* данные (та же слабость, из-за которой #106-B оказался малоэффективным, а #106-D — moot). Историческое публичное число остаётся на детерминированных гардах.
- **Blast radius: высокий** — правки хуков, UX тегирования, дисциплина пользователя, новая схема идентификаторов.
- Вывод: **отложить.** Повторяет слабость «только-будущее»; не стоит blast radius сейчас.

### C3 — Гибрид
C1 по умолчанию (бэкфиллится), C2-override когда явный тег задачи присутствует.

- Лучшее конечное состояние, но осмысленно только когда C1 доказан. **Половину C2 отложить.**

**Рекомендация: реализовать только C1. C2/C3 отложить.**

## Blast radius C1 (честный список)

|---|---|---|

| `backend/server.py` | `_today_payload`, `_productivity_block`, `_productivity_periods` — счётчики задач, семантика «sessions_covered» меняется на «task-chunks» | Средний |

| Тесты | новые unit-тесты чанкинга; существующие productivity/guard тесты перебазировать на новую единицу | Средний |

## Взаимодействие с уже отгруженными фиксами

- **#107** (merged-timeline денумератор): независим от сессий → не затронут. ✓
- **Гард #106-A**: сейчас per-session (`effective_session_hours(baseline, session_active, event_count)`). При чанкинге единица — дневной чанк. **Открытый вопрос:** trivial-stub гард применяется per-chunk (почти пустой *день* внутри настоящего марафона) или всё ещё per-session? Ошибка в дизайне здесь = либо снова течёт stub, либо ложно клампятся настоящие дни марафона.
- **Size-aware оракул #106-B**: `compute_session_metrics` → `compute_chunk_metrics` (события/active/span в рамках дня). Концептуально чисто; блок SESSION SIZE уже обобщается.

## Миграция и откат

- Ограничение **append-only / `correction_of`** (по #106): добавляются chunk-ключёванные записи; session-ключёванные не переписываются деструктивно — миграция пишет новые task-chunk записи; читатели предпочитают chunk-ключи, фолбэк на session-ключ.
- **Фичефлаг на путь агрегации** в `summarize_productivity` (session-mode vs chunk-mode), чтобы снапшот можно было регенерить обоими способами и детерминированно посчитать before/after до сдвига публичного числа.
- Откат = вернуть флаг в session-mode; chunk-записи аддитивны и инертны при выключенном флаге.

## Открытые вопросы (решить на ревью)

1. **Только C1, или сразу строить и C2 (явные теги)?** (Рекомендация: только C1.)
2. **Ключ чанка**: `session_id:date` (просто, календарный день) vs более тонкая task-id схема. (Рекомендация: `session_id:date`.)
3. **Гранулярность гарда #106-A при чанкинге**: per-chunk или per-session? (Нужно явное правило — предлагаю per-chunk, т.к. stub-*день* ничего не вносит и калибровочное разделение держится на уровне чанка; проверить таким же calibration-repro, как в #106-A.)
4. **Сдвиг публичного числа**: #106-C сдвинет all-time ×N (вероятно вверх). Тот же governance, что #106-A (before/after таблица в PR, твой гейт, деплой)? (Рекомендация: да, идентичный governance.)
5. **Объём исторического перечанка**: только сессии с живым транскриптом можно переоценить по дням; сессии с вырезанным транскриптом можно перебакетить структурно, но не переоценить — их единственный старый baseline пришлось бы либо эвристически делить, либо оставить одним чанком. (Рекомендация: live-transcript сессии получают настоящие per-day оценки; pruned оставляем одним чанком = текущее поведение, всё так же под гардом #106-A.)
